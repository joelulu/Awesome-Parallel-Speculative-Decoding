# 科研星际图 · 方法论

把一个研究方向变成一张可交互、可追溯、可持续更新的地图。DFlash Atlas 是这套方法的第一个站点；同样的流程应当能套到任何"有一篇奠基论文、之后不断有人改进"的技术方向上。

---

## 1. 这套方法解决什么

综述文章按主题分类，读起来线性；引用图按引用计数连边，看不出技术关系；awesome list 只有链接，没有判断。
三者的共同缺口是：**读者无法回答"这两个方法到底是什么关系，凭什么这么说"**。

星际图的回答方式是：每个方法是一个节点，每条边都有明确语义和证据链接，节点位置按研究问题聚类而不是按时间或引用数。

因此有一句硬约束：**图上任何一根线，都必须能被点开并落到一张表、一段正文或一个官方仓库上。** 没有证据的关系宁可画成"待核实"，也不能省略语义。

## 2. 三种关系，三种获取成本

| 关系 | 含义 | 数据来源 | 自动化程度 | 数据字段 |
|---|---|---|---|---|
| **引用** `cites` | A 的参考文献里有 B | OpenAlex `referenced_works` / `cites:` 过滤 | 全自动 | 论文 ID 对 |
| **实验** `baseline` | A 的主实验里把 B 当基线或对照 | 必须读正文表格与实验设置 | 半自动（抽取 + 人工核验） | 表号、模型、并发、指标、结论数字 |
| **技术** `extends` / `combines` / `reuses` | A 改进了 B 的某个模块，或组合了两者 | 必须读方法章节 | 人工判断为主 | 具体模块 + 证据位置 |

这是整套方法的核心判断：**引用关系便宜，实验关系昂贵，技术关系最贵。** 三条线的成本差一到两个数量级，所以流水线必须分层，不能指望一次抓取就把图建完。

DFlash 的实测数据可以校准预期：OpenAlex 显示 DFlash 被引 155 次，仓库最终收录 83 个方法、79 条关系。也就是说**引用池里有近一半的工作不值得入图**——它们只是提到 DFlash，并没有改进它。这层筛选正是人（或带证据约束的模型）不可替代的地方。

## 3. 数据源实测结论（2026-11 核对）

| 源 | 能拿到什么 | 限制 | 在流水线里的角色 |
|---|---|---|---|
| **OpenAlex** | 论文身份、DOI、发表日期、venue、作者、参考文献、被引列表、related_works | 按次计费 `$0.001`；无 key 共享 `$0.10/天`（约 100 次），免费 key `$1/天`（约 1000 次） | **主骨架**：种子定位 + 一次调用拿全部后续 |
| **arXiv API** | 最新预印本，按提交日期排序，可按分类与关键词检索 | 无引用数据，返回 Atom 需自己解析 | **增量发现**：补 OpenAlex 索引延迟（实测可当天拿到 11-19 的新论文） |
| **Semantic Scholar** | 相似论文推荐、引用上下文 | 无 key 常态 429，需申请 key | 可选补充，不建议作为主链路 |
| **Connected Papers / Litmaps** | 共引相似性可视化 | 闭源、无公开 API、不能自动化 | 人工补漏与交互设计参考 |

关键实测：`GET /works?filter=cites:W7128006584` 一次返回 155 条被引记录，前八条依次为 DSpark(108 次被引)、Domino(54)、DDTree(43)、D-PACE(32)、DMax、HunyuanOCR、JetSpec(21)、Draft-OPD(18)，与仓库人工收录高度吻合。**这说明"给一篇论文，自动铺开后续网络"在数据层已经成立，缺的是筛选与判断。**

注意 OpenAlex 的计费是新增项，脚本必须缓存响应，同一 work 不要重复请求。

## 4. 从一句话到一张图：五步

### 第 1 步 · 锁定种子

输入可以是论文名、方法名、arXiv ID 或一个研究问题。先做身份消歧：同名方法、预印本与正式版、方法名与论文标题不是一回事。

产出 `atlas.config.json`：

```json
{
  "slug": "dflash-atlas",
  "title": "DFlash Atlas",
  "root": { "name": "DFlash", "arxiv": "2602.06036", "openalex": "W7128006584" },
  "scope": "以 DFlash 为起点的并行投机解码后续方法",
  "categories": ["架构", "因果", "树与路径", "验证预算", "训练", "跨轮复用", "多模态"],
  "outOfScope": ["纯 EAGLE 系投机解码", "与 block diffusion 无关的 dLLM 工作"],
  "sources": ["openalex", "arxiv", "official-code"]
}
```

### 第 2 步 · 铺候选池（自动）

- OpenAlex `cites:<root>` 拿全部后续候选，记下被引数与日期
- OpenAlex `referenced_works` 拿上游（这个方法建立在谁之上）
- arXiv 按 `all:"<关键词>"` + 提交日期增量扫描，补最近两周
- 官方代码仓库（论文首页给出的 GitHub）核对是否存在、是否可访问

产出 `candidates.json`：候选论文 + 元数据 + 去重后的论文唯一键（DOI 优先，arXiv ID 次之）。

**这一步只决定"要不要读"，不决定"要不要入图"。**

### 第 3 步 · 逐篇判断（半自动，最贵的一步）

每篇候选回答四个问题，答案必须带证据位置：

1. 它解决了什么问题（这个方向当时卡在哪）
2. 它怎么做（一句话机制）
3. 它的主实验把谁当基线、在哪个表、什么设置、结论数字
4. 它与种子的关系属于哪一类

判断规则：
- **入图**：提出了新方法、且与种子存在技术或实验关系
- **只记录不入图**：复现、综述、应用移植到无关任务
- **待核实**：拿不到正文、只有摘要、作者未公开代码

产出方法对象（字段与 `src/data/methods.json` 一致）：`problem` / `solution` / `summary` / `benchmarks` / `relations` / `citationStatus`。

### 第 4 步 · 校验与入图

`npm run validate` 会拦截：论文 URL 重复、日期格式错误、关系端点不存在、自环、基准基线非法、日报引用了不存在的方法。
校验通过后站点自动生成节点位置（按 `category` 聚类）与连线，无需手工摆位。

### 第 5 步 · 增量维护

只做两件事：**每周扫一次被引增量**（OpenAlex `from_publication_date`），**每天扫一次 arXiv**（可直接接入 CI）。
新论文先落 `candidates`，通过第 3 步才进 `methods`。历史结论不因为新论文出现而改写，只追加"后续工作"。

## 5. 证据分级

沿用站点现有口径，四档不可混用：

| 字段 | 取值 | 含义 |
|---|---|---|
| `status` | `verified` | 已核对正文与官方来源 |
| | `imported` | 从摘要或二手来源录入，未核对正文 |
| `citationStatus` | `confirmed` | 引用关系已确认 |
| | `unconfirmed` | 引用了但未逐条核实 |
| `relations.status` | `verified` | 关系有正文证据 |
| | `proposed` | 推断关系，需复核 |

### 两个轴，不要混成一个数

**重要性**回答「值不值得读」，**证据等级**回答「我们有多确定」。两者混用会同时失真：一个划时代的工作如果只录了摘要，它的重要性不该被下调；一个精心核过的小改进也不该被抬成奠基工作。

- 重要性由 `npm run rescore` 从结构信号算出（被用作基线次数、被继承次数、可核验实验数、是否方向首篇、是否有代码），配额锁死在 10% / 23% / 38%，每个分数都带一句 `importanceBasis` 说明它怎么来的。**不接受手改 JSON**：手改会让下一个人无法判断某个分数是算出来的还是拍出来的。
- 证据等级折叠成三档展示：`已核验`（verified + confirmed）、`待复核`（verified + unconfirmed）、`导入未核验`（imported）。星图上待复核节点画成空心，卡片与方法库页显示角标，方法库支持「仅看已核验」筛选。

已知偏差：未深度整理的方法因为缺关系和实验记录，结构分会偏低。所以 **2–3 分不等于工作不重要，只代表当前证据不足**，这一点必须在报告里写明，否则评分会变成新的误导。

## 6. 一条关系如何同时服务两张卡片

实验关系是双向的：A 把 B 当基线，意味着 B 的卡片上要出现"后来 A 拿我当基线"。
所以 `benchmarks.json` 里一条记录只写一次，由生成器同时注入两端的卡片视图——这是现有实现里最值得保留的设计，也是通用模板的核心机制。

## 7. 验收标准

一个专题站算做完，要同时满足：

1. 图谱能回答"这个方向有哪几条主线"，且每条主线都有一个代表方法
2. 随便点一个节点，四项信息齐全，至少一条证据可点开
3. 连续切换三个节点，卡片与图不同步的情况为零
4. 数据能通过校验，新增一个方法不需要改代码
5. 断网状态下站点仍可浏览（静态构建，不依赖运行时 API）

## 8. 已知边界

- **实验关系无法全自动**：表格结构千差万别，抽取必须回到原文核对，否则会造出漂亮但错误的图
- **跨领域复用未验证**：目前只在"单一种子 + 明确后续"的技术方向上验证过；换成多学科交叉议题，聚类方式与关系定义都要重新设计
- **冷启动成本高**：第一篇论文之后的 20-30 个方法必须逐个读，之后才进入增量维护的低成本区间
